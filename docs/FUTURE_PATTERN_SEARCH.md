# 별도 후속 제품 구상 — 공통 캔들 패턴 검색 엔진 (아직 미구현)

## 사용자 제공 화면 설계의 의미

```
업비트 DB (현재 수집기: upbit_candles.sqlite3) ─┐
                                           ├─> 공통 검색 엔진 (engine.py, 예정)
빗썸 DB (현재 수집기: bithumb_candles.sqlite3) ─┘
                                                     ↓
                                              사용자 맞춤 수식 모듈
                                                     ↓
                                          통합 결과 / CSV 내보내기
```

기획 화면의 예시 파일명 `upbit.sqlite3`, `bithumb.sqlite3`는 **도식의 표현**이다. 실제 수집기 코드를 확인한 DB 파일명과 혼동하거나 임의로 이름을 변경하지 않는다.

- 공통 엔진은 두 SQLite DB를 **읽기 전용**으로 열고, 종목·시간봉별 완료 캔들을 시간순으로 정렬해 입력으로 제공한다.
- 사용자별 조건은 예컨대 `EMA 골든크로스 AND 4캔들 급증`처럼 결합식으로 표현하며, 결과는 True/False로 해석한다.
- 결과 컬럼 구상: 거래소, 종목, 봉 종류, 발생 시각, 가격, 적용 조건, CSV.
- 재사용 가능한 공통 검색 엔진과 교체 가능한 사용자별 규칙을 분리하여 고객마다 검색 프로그램 전체를 다시 만들지 않는 것이 목표.
- 개인용 업비트 8개 봉 설정과 판매용 11개 봉은 다른 요구사항이며 서로 섞지 않는다.

## 구현 전 의사결정 (아직 미승인)

- **설계 A:** 고객별 `.py` 동적 모듈을 import하여 수식을 실행. 빠르고 유연하지만 임의 코드 실행/악성 파일 위험이 큼.
- **설계 B (권장):** 제한된 수식 DSL/등록 함수와 검증된 입력 데이터로 규칙을 실행. 사용자 확장이 상대적으로 안전하고 보수·검증이 쉬움. 함수 확장 관리와 파서 구현 비용은 추가.
- 현재 버전에서 `engine.py`, 맞춤 규칙 실행, 통합 검색 및 검색 결과 CSV는 **구현되지 않았다**. 캔들 수집기 판매 완성률 85%에 포함하지 않는다.
- 실제 개발 시 별도 사용자 승인 후 시작하고, 원본 수집기 DB를 수정하지 않는 읽기 전용 구조부터 설계한다. SQLite WAL/동시 기록의 읽기 일관성, 시간대 변환, 중복, 성능, 저장량, 사용자 수식 실행의 보안을 검증해야 한다.
