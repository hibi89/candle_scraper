# Coin Analyzer P3 — canonical P1/P2 customer entry + offline report (2026-11-11 KST)

## Priority and architecture decision
The user wants meaningful movement from the command-center Coin Pattern Analyzer **50%** towards **70% final-product readiness**.

Two independent batch approaches existed in parallel:
- Draft PR #1 `feature/custom-batch-rule-engine`: different JSON DSL and separate interpreter, proven 57 local tests after hardening; isolated, unmerged.
- The canonical `feature/candle-pattern-analyzer` branch now has `custom_formula_scanner.py` (P1) and `custom_formula_batch.py` (P2). P2 **reuses the P1 compiler and evaluator**, supports 16 rules/8 DBs, outputs identical P1 CSV schema and formula SHA256.

**Selected:** use the canonical P1/P2 source unchanged. Introduce one customer-facing CLI `coin_analyzer.py` delegating `--rule` to P1 and `--rules` to P2; add a separate optional `coin_report.py` for offline HTML. No second batch DSL bundled or merged, no customer data sent externally. This is less maintenance and better compatibility than merging both batch algorithms.

## Customer workflow
Python 3.11+ with installed Python; BAT launchers only forward options (not EXE):
```
python coin_analyzer.py --rule examples/custom_rule_single_example.json --validate-only
python coin_analyzer.py --rules examples/customer_formula_batch_p2.json --validate-only
python coin_analyzer.py --db "C:\\candles\\upbit_candles.sqlite3" --rules examples/customer_formula_batch_p2.json --output "C:\\reports\\signals.csv" --markets BTC,ETH --units 1,5,240 --last 10000 --max-matches 500000
python coin_report.py --csv "C:\\reports\\signals.csv" --output "C:\\reports\\signals.html"
```
Repeat `--db` for distinct source DBs. Use `--rule` for one P1 JSON `{"version":1,"name":"...","when":{...}}`, or `--rules` for P2 `{"version":1,"rules":[{"name":"...","when":{...}}]}`. Both formats use the **same** canonical indicator condition syntax; only the envelope differs.

If reporting fails, a separately completed CSV is retained. The report process never opens source SQLite. Preview is first 120 rows, while counters cover all accepted CSV rows (up to 1,000,000). This is an offline historical signal catalog, **not** a forecast, profit, or live fill report.

## Code changes
- `coin_analyzer.py`: one CLI, mutual exclusive P1 single / P2 batch modes, same market/unit/last/match-limit/overwrite flags, rule-only validation without opening DB, no rewritten indicator algorithms.
- `coin_report.py`: source-independent CSV parser for canonical P1/P2 fields (also accepts experimental draft-P0 batch field names to ease historical artifact comparison). Validates CSV schema and finite positive closes, bounds input size/rows/cell size, escapes all untrusted strings, generates CSP script/network-disabled HTML, group totals + preview, publishes via exclusive same-folder link or explicit replace. Does not modify source CSV or DB.
- `start_coin_analyzer.bat` and `start_coin_report.bat`: optional Python-installed Windows launchers, not packaged EXEs.
- `examples/custom_rule_single_example.json`.
- `test_coin_cli_dispatch.py`: eight local mock-dispatch tests for CLI argument routing/validation.
- `test_coin_report.py`: thirteen actual synthetic CSV and batch-CSV tests (canonical P1/P2 header, rollback, HTML injection safety).
- `test_coin_analyzer.py`: four **full primary checkout integration tests** for actual P1/P2 single/batch CSV byte-parity, rule-only validation, HTML P2 output and output preservation.
